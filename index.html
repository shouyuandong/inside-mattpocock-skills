01

它要解决什么

这些技能面向真实工程，不靠感觉写代码。README 把常见问题归纳成四类，每一类配一组技能来应对。

GSD、BMAD、Spec-Kit 这类工具想把整个流程包下来，代价是控制权交出去，流程本身出了问题也更难改。这个仓库反过来做：技能小、能改、能拼，也不绑定某个模型。

Failure mode 01

结果不是我想要的

最常见的问题是双方理解不一致。你以为 agent 听懂了，看到成品才发现完全不是那么回事。解决办法不是把 prompt 写得更长，而是先让它反过来问你。/grill-me 和 /grill-with-docs 会一轮轮提问，把方案里每个还没定的点问清楚。

Failure mode 02

自造词与重复

agent 不了解项目里的说法，只好自己造词，同一件事也要反复解释。办法是给它一套共享词汇：GLOSSARY.md 定义领域词，ADR 记录不好解释的决定。README 的例子把一段长解释压缩成「materialization cascade 有问题」。

Failure mode 03

代码不能跑

需求对齐了，代码仍可能跑不起来，缺的是能快速验证的手段：静态类型、浏览器访问、自动化测试。/tdd 提供红绿循环，/diagnosing-bugs 把调试拆成几个阶段，每步都有明确的进入条件。

Failure mode 04

代码越写越乱

agent 写得快，代码也乱得更快。办法是持续维护设计。/to-spec 在写规格书前先问你要动哪些模块，/improve-codebase-architecture 定期扫描可深化的模块。

始终小步前进，每一步都经过深思。反馈的速度，就是你的速度上限。《程序员修炼之道》· David Thomas、Andrew Hunt

四种失败模式对应四层防线：先对齐，再共享语言，再建立反馈，最后维护结构。技能之间的依赖也沿着这条线组织，后面几节展开。

02

仓库地图

技能按工作场景与维护状态分组（bucket）放在 skills/ 下。分组不只是把技能分开放，它还决定一个技能是否随插件发布、有没有给人看的文档页。

分组数量随插件发布定位
engineering/20是日常写代码用的技能
productivity/7是通用的非代码工作流
misc/4否保留但很少用，已冻结、不维护
in-progress/8否公开测试，想收集反馈，不进插件
deprecated/0否不再使用

发布分组的硬性要求

engineering/ 与 productivity/ 是发布分组。一个技能进入这两个分组，必须同时满足三件事，否则 CI 会拦下：

Rule 01

顶层 README 有条目

技能名必须链接到它自己的 SKILL.md，并分成用户触发、模型触发两类。

Rule 02

plugin.json 在册

.claude-plugin/plugin.json 的 skills 数组逐个列出发布技能，插件发布的就是这份名单。

Rule 03

配一页给人看的文档

每个发布技能在 docs/<bucket>/<name>.md 有一页。固定三节：做什么、什么时候用、在流程里的位置；再加常见问题和「怎么判断它在起作用」两节，前置条件和其他章节按需补。

一个例外

docs/ 里现有 29 个 Markdown：27 个发布技能页、1 个 docs/agents/triage-labels.md、1 个 resolving-merge-conflicts.md。最后这个是已移除技能的归档页，按规则保留，保证旧链接还能打开。

每个 SKILL.md 的两种触发方式

所有技能只按一个标准分类：谁能触发它。Claude Code 和 Codex 里的划分必须一致，否则同一个技能在两个工具里的表现会不一样。

类型谁能触发标记方式description 写给谁
用户触发 只有输入 /name disable-model-invocation: true + policy.allow_implicit_invocation: false 人。一句话说清楚，去掉触发短语
模型触发 人或模型 默认，不写这两个开关 模型。保留「当用户想要…、提到…」这类触发措辞

依赖只能朝一个方向：用户触发的技能可以调用模型触发的技能，但不能调用另一个用户触发的技能。写依赖时要明确写「调用 Skill 工具」，不能只留一个 /name 让模型自己猜。

写作约束

仓库里的正文一律不用长破折号，包括 SKILL.md、docs、README、CHANGELOG、ADR。需要停顿时改用逗号、冒号、句号、括号或连词。另外，凡是会把任务交给 subagent 的技能，都必须要求 subagent 从全新的上下文开始，因为 fork 会继承父对话的上下文，而 subagent 的意义就是避开这份上下文。

安装与分发

这套技能有两种安装方式：插件自动更新，和通过 skills.sh 安装，为了避免重复安装，两种方式选一个即可。

Agent安装方式自动更新
Claude Code@claude-plugins-official默认自动
Codex@mattpocock marketplace启动时
Copilot CLI@mattpocock marketplace一次性配置后
VS CodeChat: Install Plugin From Source每天
Gemini CLIgemini skills install（复制）手动重跑
其他 agentnpx skills@latest add手动 update

三步上手

claude plugin install mattpocock-skills@claude-plugins-official

装完在每个仓库跑一次 /setup-matt-pocock-skills。它会问三件事：issue 放在哪里（GitHub、GitLab、本地 Markdown，或你指定的其他工具）、triage 用哪些标签、生成的文档存在哪。答案写进 docs/agents/*.md，后面的技能都从这里读配置。

为什么 Claude Code 有原生插件，Codex 一开始没有

ADR 0002 记录了这个取舍。技能按分组存放，插件只能带上 engineering/ 和 productivity/ 这两个分组里的 27 个，不能带上 misc/ 和 in-progress/。

Claude Code
plugin.json 的 skills 接受路径数组，可以逐个列出要发布的技能，不会多也不会少。
当时的 Codex
skills 只接受单一路径字符串，并且会递归查找里面所有 SKILL.md。指向 ./skills/ 会连 in-progress/、misc/ 这类不发布的分组一起发布；用符号链接拼一个扁平目录，安装时符号链接会丢失，技能变成空目录。
当时的取舍
先发 Claude Code 插件，Codex 和其他工具继续用 skills.sh。等 Codex 支持数组或保留符号链接再补。
2026-10-08 更新
Codex main 已接受 skills 字符串数组，并在没有 .codex-plugin/ 时回退读 .claude-plugin/。这条约束消失，@mattpocock marketplace 成了 Codex、Copilot、VS Code 的主要安装方式。
2026-08-05 更新

plugin.json 的 version 跟 package.json 同步。Release 工作流跑 npm run version，由 scripts/sync-plugin-version.mjs 复制版本号。Claude 用这个字段判断已安装用户何时看到更新。

04

主流程：从想法到发布

/ask-matt 负责指路：它把 27 个发布技能画成一张图。大部分工作沿一条主线走，另外有三个入口可以切进来。

  1. 对齐：/grill-with-docs

    在有工作目录时从这里开始。它同时调用 grilling 和 domain-modeling，一边追问，一边把术语写进 GLOSSARY.md、把难以逆转的决定写成 ADR。没有工作目录就改用 /grill-me，它不留下任何文件。

  2. 分叉：问题能在对话里解决吗？

    如果某个问题必须跑起来才能回答，例如状态模型、业务逻辑、需要看到的 UI，就绕道 /prototype。原型放在自己的目录里，用 /handoff 把上下文带出去，做完再 /handoff 把结论带回来。

  3. 分叉：这个工程一次对话做得完吗？
    • 是：/to-spec 把对话整理成规格书，/to-tickets 拆成一个个 tracer bullet ticket，每个写明它依赖哪些 ticket。然后二选一：/implement 逐个实现，每个之间清上下文；或 /implement-spec 把 ticket 当任务图，把已经没有前置依赖的 ticket 并行交给 implementer subagent，全部落到一条集成分支。
    • 否：/implement 就在当前上下文里做完。

    两条路都由 /tdd 驱动实现，最后用 /code-review 从代码规范和需求两个角度各审一遍。

  4. 出 PR：/pr

    PR 正文只留三块：用最简单的图说清改了什么、改前改后的对比证据、合并风险（能不能回退，影响范围多大）。它是模型触发技能，agent 写 PR 时会自己取用。

  5. 收尾：/retro

    回顾这一场对话，但改进对象是 agent 的工作环境，不是这次的代码：项目里怎么找信息、自动化检查、编码标准、steering 文件、工具链。能用脚本自动查的就不靠人记，剩下的判断写成编码标准。下一次工作从更好的环境开始。

上下文管理

第 1 到第 3 步用同一份上下文，中间不要清空，直到 /to-tickets 之后才重置，这样追问、规格书和任务拆解都建立在同一份思考上。每个 /implement 再从一个 ticket 开始，用全新的上下文。上下文有一个有效上限，ask-matt 技能给的经验值是约 150k tokens，超过后判断力开始下降；快到这条线时，就在阶段交界处 /compact，不要在状态变差时硬撑。

三个入口

On-ramp

/triage

bug 和外部请求堆积时用。它把 issue 或外部 PR 依次推进五个状态，整理成 agent 可以直接开工的说明。它只处理别人提的 issue；/to-tickets 产出的 ticket 已经写好，可以直接开工，不用再 triage。

On-ramp

/diagnosing-bugs

疑难 bug、偶发 flake、在两次确认正常之间悄悄出现的回归。没有能快速复现的办法，它不会开始猜原因；修完还要在合适的位置补上回归测试。

On-ramp

/wayfinder

一次对话做不完的大工程。它不直接做交付，而是在 issue tracker 上画一张共享地图，逐个解决待定事项，把未知范围逐步收窄。地图清晰后交给 /to-spec，不直接进 /implement。

06

五个关键机制

技能有 39 个，整套方法真正依赖的概念只有几个。先弄清这几个，比记住全部名字更有用。

1. grilling：先问现在能回答的问题

/grilling 是最底层的追问流程。grill-me、grill-with-docs、triage、wayfinder 和 improve-codebase-architecture 都在内部调用它。

Mechanism

问题之间有先后

每个决定都会带出几个依赖它的子决定。前置条件已经满足、现在就能回答的，是眼下这一批问题。每轮只问这一批，等用户回答后再看下一批。

Mechanism

事实归 agent，决定归人

需要查文件、查环境的事实由 agent 派 subagent 去找，不拿来问用户。真正需要取舍的交给用户，并附上推荐方案。眼下能问的都问完，用户也确认没有遗漏，访谈才结束。

2. tight loop：先能复现，再猜原因

/diagnosing-bugs 的第一阶段就是整个技能。它要求有一条已经亲手跑过的命令，同时满足四个条件：能让这个 bug 重现、每次结果一致、几秒钟跑完、agent 可以无人值守地跑。

做不到就明确停下，列出试过的方法，向用户要环境访问权限、脱敏后的真实数据，或临时在生产环境加监测的许可，而不是继续读代码、凭猜测推演。这是仓库里最严格的一条前置要求。

3. deep module：接口小，藏的行为多

/codebase-design 规定只能用一组固定的词，不许换成 component、service、API、boundary。

词含义
Module任何有接口和实现的单元，可以是函数、类、包，或跨层的一组代码
Interface调用方必须知道的一切：签名、约束、调用顺序、出错方式、配置、性能表现
Depth接口背后藏了多少行为。接口很小、背后行为很多，就是深；接口和实现一样复杂，就是浅
Seam不用改这里的代码就能改变行为的位置，通常就是接口所在之处
Leverage调用方从「深」里得到的好处：学一次接口，就能用在 N 个调用点和 M 个测试上
Locality维护方从「深」里得到的好处：修改、缺陷、相关知识、验证都集中在一处

最常用的是两条判断标准。一是试着删掉它：复杂度随之消失，说明它没必要；只是散到 N 个调用方那里，说明它确实有用。二是看有几个实现：只有一个 adapter，这处接口可能只是设想；有两个，才说明它真有必要。

4. tracer bullet：一个 ticket 走通一条路

/to-tickets 不按代码层拆。每个 ticket 覆盖的范围不大，但从头到尾走得通，会同时改到 schema、API、UI 和测试；单独做完就能演示、能验证，也能放进一个全新的上下文窗口。

每个 ticket 写明它依赖哪些 ticket：哪些必须先做完。没有前置依赖的 ticket 可以同时开始。大范围重构是唯一例外：一次机械式重命名会同时改坏上千个调用点，没有哪个 ticket 能单独做完还让测试全过。这类工作分三步：先加新写法，旧写法留着；再分批把调用换过去；确认没人用了，再删掉旧的。

5. 两种负担与一个选词技巧

Concept

context load 与 cognitive load

context load 是常驻上下文每一轮都要占用的 token 和注意力。cognitive load 是人要记住「有哪些文档、什么时候该用」的负担。后者不该一味削减，它本来就是要由人来承担的判断成本。

Concept

leading word

挑一个模型在训练数据里见过的词，让它一次代表一串要求，例如用 tight 表示「快、稳定、开销小」。之后重复这个词，不要重复整句解释。自己造词就得先解释一遍，能用现成的词就别造。

/writing-for-agents 还指出一个反直觉的点：你在指令里写「不要做 X」，反而把 X 摆进上下文，让它更容易被想到。「不要想大象」的结果是大象占满脑子。应该直接写希望它做什么。

07

写自己的 skill

仓库对这件事有完整的方法，集中在 /writing-for-agents。下面每一条都可以直接照着做。

先决定谁能触发

如果只能靠人判断什么时候该用它，就设成用户触发；如果模型自己就能判断，就保持模型触发。这个选择也决定 description 怎么写。

---
name: my-skill
description: 一句话说明它解决什么问题。
disable-model-invocation: true
---

把 description 写成索引

description 就是一条索引：说清这份材料是什么，以及什么情况下该来取。每种情况只写一个触发词，换个说法不算新情况。常驻的每个字每一轮都在花 token，所以索引比正文更该精简。

给每一步写完成标准

完成标准要能检查，也要覆盖所有该做的工作。「理解到位」这种说法太松，agent 觉得差不多就收手；「每个改动涉及的领域概念都说清楚了」才能逼出真正要做的事。先把标准定明确，实在说不清的，再考虑把后续步骤放到下一次上下文里。

按信息层级摆放内容

从上到下三层：文件里的步骤、文件里需要时再看的参考、单独成文并靠索引引用的参考。每条路径都要用的写在同一处，只有部分情况才用的放到下层。同一个概念的定义、规则、注意事项要放在一起，不要分散。

修剪

  • 每个含义只有一个权威出处。重复会让它显得比实际更重要，也会让修改变成多处编辑。
  • 环境本身就是事实来源。package.json 的脚本、目录结构、--help 输出，文档再抄一遍只是多一份会过期的副本，只有查起来很费劲时才值得。
  • 逐句看有没有废话：模型本来就会照做的指令，整句删掉，不要只删几个词。
  • 警惕层层堆积：旧内容因为「加着安全、删了危险」而留下，最后要挖很久才能找到还有用的部分。
仓库自己的例子

CLAUDE.md 只有 4.2 KB，AGENTS.md 只有 9 字节。规则没有堆在常驻文件里，而是分散到 .agents/ 下的专题文档，由一行索引按需引入。这正是「少占常驻上下文、需要时再展开」的做法。
